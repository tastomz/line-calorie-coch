# Backup and recovery

## Status

| Item | State |
| --- | --- |
| Application-level backups | **not implemented** (by design) |
| Managed Postgres backups | **documented** — **not configured** by this repo |
| Point-in-time recovery | **documented** if your provider supports it — enable in the cloud console |
| In-app restore button | **not implemented** |

If backups are not configured on the database host, **assume data can be lost**.

---

## PostgreSQL (production target)

### Approach (**documented**)

Use the managed provider’s automated backups (continuous WAL + daily snapshots),
or `pg_dump` / `pg_basebackup` on a schedule if self-hosting.

### Frequency (recommendation)

| Tier | Frequency |
| --- | --- |
| Point-in-time recovery (PITR) | Continuous WAL if available |
| Full snapshot | At least daily |
| Pre-migration dump | Immediately before schema migrations |

### Retention (recommendation)

- Daily snapshots: **14–30 days**
- Weekly snapshots: **8–12 weeks** (optional)
- Keep one known-good dump from the last successful deploy

### Restore procedure (outline)

1. Stop writers (scale app to 0 or block webhooks) so restore is consistent.
2. Restore from snapshot or `pg_restore` into a new database instance.
3. Point `DATABASE_URL` at the restored instance.
4. Run `npx prisma migrate deploy` only if the dump is from before pending migrations.
5. Smoke-test: webhook signature, food confirm, daily summary (`docs/SMOKE_TEST.md`).
6. Re-enable traffic.

### Migration rollback strategy

- Prefer `prisma migrate deploy` (forward-only) in production.
- Take a dump **before** applying migrations.
- Test migrations on a staging clone first.
- Prefer **forward-fix** migrations over downgrade scripts.
- Never run `migrate reset` / `db push --force-reset` against production.
- If a bad migration is deployed: restore from pre-migration backup, redeploy previous app image.

### Disaster recovery considerations

| Data | Recoverable? |
| --- | --- |
| Users, FoodLogs, WeightLogs, profiles | Only if Postgres backups exist |
| Google Sheets rows | Reporting copy only — **not** a restore source of truth |
| LINE chat history | Not stored as SoT in this app |
| Pending food analyses | Transient; users can re-send meals |
| LineEvent idempotency keys | Regenerated by traffic; retention cleanup may delete old rows |

Without a configured backup, recovery = **re-onboard users and re-log data**.

## SQLite (local / non-production)

Copy `prisma/dev.db` (or the file referenced by `DATABASE_URL`) while the app is stopped.
SQLite file copies are for developer convenience only — not a production strategy.
